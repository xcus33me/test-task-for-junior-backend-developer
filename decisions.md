# Проектные решения

## Расписания

Самый простой вариант решения задачи - это добавить в таблицу `tasks` поля периодичности (6+ полей: `recurrent_type`, `every_n_days`, `day_of_month`, `specific_dates` и т.д), но тогда у каждой задачи появились бы поля, которые зачастую им не нужны.

Вместо этого я решил сделать отдельную сущность `Schedule` - это шаблон задачи (название, описание) с правилами повторения. Из нее автоматически (с помощью фонового воркера) генерируются обычные задачи, которые тоже можно редактировать, закрывать, удалять через тот же API.

Это позволяет разделять жизненные циклы. Расписания живут отдельно от задач - их можно деактивировать, задачи при этом остаются. Если бы правила хранились в самой задаче, непонятно где жил бы "шаблон" между созданиями экземпляров.

## Фоновый воркер и ручной эндпоинт

Воркер генерирует задачи на сегодня при старте приложения и дальше раз в час. Также есть эндпоинт `POST /schedules/generate` для двух случаев: сгенерировать задачи наперёд (например, на завтра) или повторно запустить генерацию, если что-то пошло не так.

## Дедупликация

Чтобы одна и та же задача не создавалась дважды (например, если воркер запустился два раза, или пользователь нажал `generate` повторно), в миграции стоит *уникальный индекс* на `(schedule_id, scheduled_date)`. Если задача уже есть - вставка просто игнорируется.

## Даты в формате строки (YYYY-MM-DD), не timestamp

Периодичность оперирует календарными датами, а не моментами времени. Передавать `2025-01-15` понятнее и проще, чем `2025-01-15T00:00:00Z`.

## Corner cases

**`monthly` и короткие месяцы.** Если выбрано 31-е число, а в месяце 28 или 30 дней - задача в этом месяце не создаётся.

**`daily` с `every_n_days = 1`.** Эквивалент "каждый день". Отдельного типа `every_day` нет — это частный случай `daily`.

**`specific_dates` с датами в прошлом.** Допускаются - пользователь может создать расписание задним числом для истории или регенерации задач.

**Повторный вызов генерации.** Безопасен. Уникальный индекс `(schedule_id, scheduled_date)` гарантирует что дубликаты не создадутся - вставка молча игнорируется.

**Удаление расписания.** Уже созданные задачи остаются - у них просто обнуляется `schedule_id`. 

**`end_date` раньше сегодня.** Расписание существует, но воркер его пропускает — `MatchesDate` вернёт `false` для любой даты после `end_date`.

## Типы периодичности

| Тип | `recurrence_type` | Описание | Обязательные поля |
|-----|-------------------|----------|-------------------|
| Ежедневная | `daily` | Каждый N-й день от `start_date` | `every_n_days` (по умолчанию 1) |
| Ежемесячная | `monthly` | Определённое число каждого месяца | `day_of_month` (1–31) |
| Конкретные даты | `specific_dates` | Только на указанные даты | `specific_dates` (массив дат) |
| Чётные дни | `even_days` | Чётные числа месяца (2, 4, 6, ...) | — |
| Нечётные дни | `odd_days` | Нечётные числа месяца (1, 3, 5, ...) | — |

## Примеры запросов

Создание ежедневного расписания (каждые 2 дня):

```json
POST /api/v1/schedules
{
  "title": "Обзвон пациентов",
  "description": "Ежедневный обзвон пациентов палаты №3",
  "recurrence_type": "daily",
  "every_n_days": 2,
  "start_date": "2025-01-01"
}
```

Создание ежемесячного расписания (каждое 15-е число):

```json
POST /api/v1/schedules
{
  "title": "Формирование отчётности",
  "description": "Отчёт по расходным материалам",
  "recurrence_type": "monthly",
  "day_of_month": 15,
  "start_date": "2025-01-01",
  "end_date": "2025-12-31"
}
```

Создание расписания на чётные дни:

```json
POST /api/v1/schedules
{
  "title": "Инвентаризация",
  "description": "Проверка складских остатков",
  "recurrence_type": "even_days",
  "start_date": "2025-01-01"
}
```

Ручная генерация задач на дату:

```json
POST /api/v1/schedules/generate
{
  "date": "2025-01-15"
}
```
